## 1. What this application is

Analytix AI Business Transformation OS is a Next.js web application that runs an organization's AI transformation program end to end: capturing how work is actually done today (via structured, multilingual AI-led interviews with staff), turning that into SOPs, a searchable knowledge base and process maps, identifying AI opportunities, building business cases and ROI estimates, running those projects through a formal governance sign-off chain, publishing reusable AI agents, and then training staff and measuring real-world impact after go-live.

A deliberate design principle runs through the whole codebase: **nothing is fabricated.** Every SOP, business case, training module and opportunity description is generated by deterministic templates from facts an employee actually stated in an interview — there is no live LLM call inventing content, and no simulated data pretending to be a real integration or a real financial model.

## 3. Architecture

### 3.1 Request flow
Next.js App Router with three route groups:
- **`src/app/login`** — public sign-in page.
- **`src/app/interview/[token]`** — public, unauthenticated guest interview flow reached only via a shareable invite link (see §6.2). No app login required.
- **`src/app/(app)/*`** — the authenticated application. A single server-rendered layout (`src/app/(app)/layout.tsx`) checks the NextAuth session on every request and redirects to `/login` if absent; there is no separate `middleware.ts` — auth gating happens in this layout plus per-action permission checks (defense in depth).
- **`src/app/api`** — NextAuth's API route handler.

### 3.2 Server actions, not a separate API
All writes (creating a project, submitting an interview answer, generating an SOP, deciding a governance stage, etc.) go through Next.js **Server Actions** in `src/lib/actions/*.ts` — there is no separate REST/GraphQL API layer. Each action:
1. Reads the current session (`getServerSession`).
2. Calls `assertCan(role, permission)` from `src/lib/rbac.ts` — throws `ForbiddenError` if the signed-in role lacks the required permission.
3. Validates input with Zod.
4. Performs the Prisma write, usually inside a transaction where multiple related rows change together.
5. Writes an `AuditLog` row (`src/lib/audit.ts`) — every meaningful action in the system is attributable to a user and timestamped.
6. Calls `revalidatePath` for the affected pages so the UI reflects the change immediately.

## 4. Data model

25 Prisma models, organized by the phase that introduced them. Every model uses `cuid()` primary keys, and cascade deletes are used deliberately so that deleting a `Process` cleanly removes everything downstream of it (see §6.4).

**Foundation (org structure & auth):** `Organization → Country → Division → Department`, `User` (role, org, optional department headship), `AiTransformationProject` (the Section-4 "project setup" record — objective, in/out-of-scope activities, current systems, known pain points, etc.), `KnowledgeSource` (uploaded reference files), `AuditLog` (every action, actor, entity, timestamp).

**AI Interviews:** `Process` (the thing being discovered — one project can have many processes, and now many interviews per process), `Interview` (one employee's conversation; full engine state stored as JSON, plus a normalized `completeness` score), `InterviewInviteLink` (shareable, no-login link scoped to one project + one staff member, optionally targeting an existing process to gather a second perspective), `InterviewMessage` (full transcript), `InterviewStepRecord` (the walkthrough steps extracted from a real case), `InterviewObservation` (each AI-raised observation/bottleneck/risk and how the employee confirmed, partly-confirmed, or rejected it — never silently assumed).

**Process Digital Twin, SOPs & Knowledge:** `Sop` (deterministic markdown SOP per process, draft/published), `KnowledgeItem` (distinct knowledge/template statements captured across interviews, deduplicated).

**AI Opportunities & Projects:** `AiOpportunity` (one row per confirmed observation, with rule-derived LOW/MEDIUM/HIGH impact and effort bands — never a fabricated score), `AiProject` (a deterministic business case generated from one opportunity, carrying its own governance status).

**Agents, ROI & Governance:** `Agent` (a published, reusable AI agent — the productized form of an approved AI Project), `RoiEstimate` (transparent, formula-based savings estimate with documented assumptions — not a real financial model), `GovernanceStage` (the fixed 6-step sign-off chain: process owner → department head → legal/compliance → information security → AI transformation committee → management/CEO, decided strictly in order).

**Training, Continuous Improvement & Impact:** `TrainingModule` (generated from a published SOP), `ChangeRequest` (flagged issues against a published SOP), `ImpactMeasurement` (30/60/90-day before-vs-after checkpoints — reviewer-entered, since the app has no live usage telemetry), `Integration` (a registry of external systems — Odoo, Analytix360, email, WhatsApp — recorded as configured or not; no live credentials or syncing is implemented).

The schema currently runs on **SQLite** (`provider = "sqlite"` in `schema.prisma`, file `dev.db`), which is why fixed-vocabulary fields like `role` and `status` are plain strings with a TypeScript const-object standing in for a real enum (`src/lib/enums.ts`) — SQLite has no native enum type. Switching `provider` to `"postgresql"` and re-running `prisma migrate dev` is the only schema-level change needed for a Postgres production database (see §8).

## 5. Roles & permissions

Nine roles are defined (`src/lib/enums.ts` → `Role`), mirroring the organization's real functions:

Employee, Process Owner, Department Head, AI Transformation Committee, Technology Team, Information Security, Legal/Compliance Reviewer, Management/CEO, Administrator.

Access is governed by eight coarse permissions in a single matrix (`src/lib/rbac.ts` → `PERMISSIONS`), checked with `can(role, permission)` / `assertCan(role, permission)` everywhere a page or action needs to gate access:

| Permission | Who has it |
|---|---|
| `setup.manage` | Administrator, Department Head, Process Owner |
| `admin.manage` | Administrator only |
| `knowledge.upload` | Administrator, Department Head, Process Owner, Employee, Technology Team |
| `interview.conduct` | Everyone except (implicitly) pure external guests — Administrator, Department Head, Process Owner, Employee, Technology Team, Information Security, Legal/Compliance Reviewer, AI Transformation Committee, Management/CEO |
| `interview.review` | Administrator, Department Head, Process Owner, AI Transformation Committee, Management/CEO |
| `governance.review` | Administrator, Process Owner, Department Head, Legal/Compliance Reviewer, Information Security, AI Transformation Committee, Management/CEO |
| `security.view` | Administrator, Information Security, Management/CEO |
| `executive.view` | Administrator, Management/CEO, AI Transformation Committee, Department Head |

The Administrator role is intentionally included in nearly every permission — it is the operational super-role for the platform. Full deletion of a process (removing every record derived from it) is restricted to `admin.manage` specifically; the safer "delete interviews only" option (see §6.4) uses `interview.review`.

This matrix is the single source of truth: the Security module surfaces it directly to Information Security/Management rather than re-deriving it, so the access posture shown in-app is always accurate.

## 6. Core workflows

### 6.1 The AI Interview
An authenticated staff member (or a guest via invite link, §6.2) is walked through a fixed, deterministic conversation by "Alex, your Analytix AI Process Consultant" — one question at a time, in the employee's chosen language, asking them to describe their work the way they'd explain it to a new hire. As they answer:
- Walkthrough steps are recorded individually (`InterviewStepRecord`).
- The engine watches for specific patterns (duplicate data entry, dependency on a document/system, undocumented tribal knowledge, manual follow-ups, authority/approval checks, general bottlenecks) and raises an **AI Observation card** for each — the employee must explicitly confirm, partially confirm, or reject it. Nothing is assumed silently.
- On completion, captured knowledge/template statements are synced into `KnowledgeItem`, and every confirmed or partly-confirmed observation becomes an `AiOpportunity`.

### 6.2 Shareable interview invite links
From AI Interviews, an administrator/process owner can generate a no-login link scoped to one project and one pre-selected staff member. Opening the link starts (or resumes) that person's interview directly — useful for staff without app accounts. Each link can also optionally target an **existing process**, so a second (or third) staff member's perspective is gathered against the same process rather than creating a duplicate.

### 6.3 Multiple interviews per process — conflict detection & reconciliation
This was a gap identified and closed in this build cycle: previously, a process had no formal way to combine multiple staff members' descriptions of the *same* work, or to know if their accounts disagreed.

Now, when starting an interview (or generating an invite link), the interviewer can choose **"join an existing process"** instead of always creating a new one. When a second interview on the same process completes, `checkProcessForConflicts()` (`src/lib/actions/interviews.ts`) runs `compareProcessFacts()` (`src/lib/process-facts.ts`) across every completed interview on that process, comparing steps and key fields. If there is a genuine disagreement, the process is flagged `NEEDS_REVIEW` and **SOP generation is blocked** until a reviewer resolves it. The reviewer sees a side-by-side diff (`ReconcileForm`) and picks the correct value field-by-field (or accepts one interview wholesale); resolving it creates a new, reviewer-attributed "merged" interview record, fully audit-logged, and clears the process back to normal so SOP generation can proceed. If multiple interviews agree, no reviewer step is needed — the system already had a fallback ("most complete interview wins") for that case.

### 6.4 Deleting a process — cascade-aware, with a safer partial option
Because a `Process` cascades down through interviews, SOPs, knowledge items, AI opportunities, AI projects, agents, ROI estimates, governance stages, training modules, change requests and impact measurements, deleting one is consequential. Two options are provided, both showing an accurate, dynamically computed warning of exactly what will be removed before anything happens:
- **Delete everything** (`deleteProcessCompletely`, Administrator only) — removes the process and every dependent record listed above.
- **Delete AI Interviews only** (`deleteProcessInterviewsOnly`, requires `interview.review`) — removes only the Interview rows (and their messages/steps/observations), leaving the process's SOP, knowledge items, AI opportunities/projects, and governance history untouched. This is the option offered when someone wants to discard a flawed interview without losing everything built on top of the process since.

Both are surfaced from Process Discovery, Process Digital Twin and Process Maps, wherever a process can be acted on.

### 6.5 Downstream lifecycle
Confirmed observations → **AI Opportunities** (rule-derived impact/effort bands) → a reviewer generates an **AI Project** business case → **ROI Estimate** (transparent formula, documented assumptions) → **Governance** (6 fixed sign-off stages, strictly sequential) → on approval, publish as a reusable **Agent** → generate a **Training Module** from the process's published SOP → ongoing **Continuous Improvement** (change requests against SOPs) → **Impact Measurement** (30/60/90-day reviewer-recorded checkpoints against the original ROI baseline). The **Control Tower** and **Executive Overview** dashboards roll all of this up for leadership.

## 8. Current hosting posture vs. production requirements

Today the app runs **locally only**: SQLite file database, local-disk file storage, `NEXTAUTH_URL=http://localhost:3000`. To host it online on a real domain, three things need to change in the code (all straightforward, no redesign) plus several accounts/services need to exist on your side:

**Code changes required (I can do these once the live project folder is connected):**
- Point `DATABASE_URL` at a real Postgres connection string and change `provider` to `"postgresql"` in `schema.prisma`, then run `prisma migrate deploy` against it.
- Replace local-disk file storage in `src/lib/storage.ts` (used for uploaded Knowledge Source files) with a cloud object store, since serverless hosts like Vercel don't have a persistent filesystem — Vercel Blob is the natural fit.
- Generate and set a real `NEXTAUTH_SECRET` (`openssl rand -base64 32`) and set `NEXTAUTH_URL` to the real domain.

**What only you can provide/set up:**
- A purchased domain.
- A GitHub account and repository (the code needs to live somewhere Vercel can pull from — none exists yet).
- A Vercel account (or equivalent Next.js host).
- A managed Postgres provider — Neon or Supabase both have workable free tiers.
- Vercel Blob storage enabled on the Vercel project.

**Deployment sequence, once those exist:** push the code to GitHub → import the repo into Vercel → set the environment variables above in Vercel's project settings → deploy → run the Postgres migration against the production database → add the custom domain in Vercel's domain settings → point the domain's DNS (a CNAME or A record, depending on the registrar) at Vercel → Vercel auto-provisions HTTPS via Let's Encrypt.

I will not create these accounts, purchase the domain, or handle any payment on your behalf — those steps need to be done by you; I can do all of the code changes and give exact instructions for each console step when you're ready.

## 9. Known constraints (by design, not bugs)

- **No live LLM calls anywhere.** SOPs, business cases, training modules and opportunity descriptions are all generated by deterministic templates from facts captured in interviews — a conscious choice to guarantee nothing is ever fabricated.
- **ROI figures are a transparent formula**, not a financial model — every estimate ships with its own stated assumptions (case volume, cost per hour, a documented time-saved heuristic) rather than a black-box number.
- **Integrations module is a registry, not a live connector** — it honestly records "configured" vs. "not configured" for Odoo/Analytix360/email/WhatsApp; there is no real credential storage or syncing implemented.
- **Impact Measurement is reviewer-entered** — the app has no production telemetry pipeline to pull real usage numbers from, so 30/60/90-day checkpoints are recorded by a person, not measured automatically.
- **SQLite today, Postgres-ready schema** — the switch is a configuration and migration step, not a redesign (see §8).

## 10. Glossary of key statuses

- **Process status:** `IN_PROGRESS` → `COMPLETE`, with `NEEDS_REVIEW` inserted whenever two interviews on the same process disagree and haven't yet been reconciled.
- **Interview status:** `IN_PROGRESS` → `COMPLETED` (or `ABANDONED`).
- **SOP / AI Project / Training Module status:** `DRAFT` → `PUBLISHED` (SOP, Training) or `DRAFT` → `PROPOSED` (AI Project).
- **AI Opportunity status:** `IDENTIFIED` → `DISMISSED` (if a reviewer decides not to pursue it).
- **AiProject governance status:** `NOT_STARTED` → `IN_REVIEW` → `APPROVED` / `REJECTED`.
- **Governance stage status:** `PENDING` → `APPROVED` / `REJECTED`, one of 6 fixed, strictly sequential stages.
- **Agent status:** `DRAFT` → `ACTIVE` → `RETIRED`.
- **Change Request status:** `OPEN` → `IN_PROGRESS` → `RESOLVED`.
